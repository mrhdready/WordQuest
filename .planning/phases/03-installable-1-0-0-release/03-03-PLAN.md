## Phase Goal

> Another family installs, updates and restores WordQuest 1.0.0 in its home network by following one install page, without special know-how

Hinweis (MVP-Modus): Das Ziel ist nicht als User Story formuliert; eine Story-Fassung entsteht nur über `/gsd-mvp-phase 3`. Dieser Plan erfindet keine.

## Flagged Assumptions

- **Demo-Elternkonto aus einer Installation von vor Phase 1 (03-RESEARCH L2): weggelassen.** Prüfung, ob der Fall bei Installationen aus `setup.sh` real vorkommt:
  - Veröffentlicht war nur der Stand von `origin/master` (`6a918e8`, App-Code wie `4ce32da`). Die Korrekturen aus `96329c3` (lesbare Secrets, Mandanten-Claim) liegen nur auf `v1-fertig` (`git branch -a --contains 96329c3`).
  - In diesem Stand legte `setup.sh` die Secrets mit `chmod 600` an (`git show 4ce32da:setup.sh`, Zeile 36), das API-Image läuft als `USER wordquest` (`4ce32da:backend/Dockerfile`, Zeile 39), und die API liest den JWT-Schlüssel beim Start per `File.ReadAllText` vor Migration und Seed (`4ce32da:backend/src/WordQuest.Api/Program.cs`, Zeilen 18 und 158-163). Der Quick-Task belegt den roten Lauf: „Exit 1: tatsächlicher Non-Root-API-Container kann Secrets nicht lesen“ (`.planning/quick/261006-r7l-installer-rechte-lesbare-docker-secrets-/261006-r7l-VERIFICATION.md`, Zeile 14). Eine solche Installation startete die API nie; der `DemoDataSeeder` lief nie, ein Demo-Konto entstand nicht.
  - Selbst mit von Hand gelockerten Rechten hätte die App keine Familiendaten getragen: Ohne `MapInboundClaims = false` sahen Eltern und Kind leere Daten, jede falsche Antwort ergab HTTP 500 (`261006-r7l-SUMMARY.md`, Zeilen 36-43).
  - Installationen aus `setup.sh` seit Phase 1 haben kein Demo-Konto: `.env.example` hat `WQ_SEED_DEMO_DATA=false`, und `setup.sh:77-80` bricht bei `true` ab.
  - Es bleibt das Sicherheitsnetz ohne neuen Code: `DemoAccountCheck` bricht den Start ab und nennt den Befehl (`DemoAccountCheck.cs:41-43`), `upgrade.sh` verweist bei fehlender Bereitschaft auf `docker compose logs api`, und die Seite erklärt unter „Hilfe bei Problemen“, dass die Abbruchmeldung den Ausweg nennt. Das deckt sich mit D-06: `upgrade.sh` gilt für Installationen ab 1.0.0 bzw. aus `setup.sh` seit Phase 1.
- **Update-Weg bestätigt (D-05):** `git pull` und danach `./upgrade.sh`. `upgrade.sh` führt `git pull` nicht selbst aus, weil Bash das laufende Skript nachliest (03-RESEARCH A6). Der Smoke läuft in einer Arbeitskopie ohne `.git`; ein `git`-Aufruf im Skript würde dort scheitern.
- **Reihenfolge innerhalb von D-05:** D-05 nennt „Version in .env setzen, pull, up -d“. Der Plan lädt zuerst mit der Zielversion als Shell-Variable und schreibt `.env` erst danach (03-RESEARCH Befund 5). So hinterlässt ein fehlendes Image keine `.env` mit einer Version ohne Image; das erfüllt „Abbruch ohne halben Zustand“ aus derselben Entscheidung.
- **Ältere Version im Smoke:** Es gibt keine veröffentlichten Images mit Phase-1-Stand. Der Smoke benennt die lokal gebauten Images zusätzlich als `0.0.0-smoke`, startet die Installation damit und aktualisiert auf `1.0.0`. Belegt ist damit der Ablauf von `upgrade.sh` (Sicherung, Laden, `.env`, Neustart, Daten); Schema-Migrationen beim API-Start belegen die Phase-2-`MigrationTests`.
- **Kein automatisches Zurückrollen nach dem Start:** Wird die API nach dem Update nicht bereit, nennt die Meldung den Weg zurück (alte Version in `.env`, dann `./restore.sh <Sicherung>`), führt ihn aber nicht selbst aus. Das ist im Smoke nicht provozierbar und Teil der manuellen Abnahme.
- **Rechte von backups/:** `upgrade.sh` ändert keine Rechte; `setup.sh` legt `backups` mit `0700` an. Prüft nur Besitz wie `setup.sh:56` (Pitfall 8).
