## Phase Goal

> Another family installs, updates and restores WordQuest 1.0.0 in its home network by following one install page, without special know-how

Hinweis (MVP-Modus): Das Ziel ist nicht als User Story formuliert; eine Story-Fassung entsteht nur über `/gsd-mvp-phase 3`. Dieser Plan erfindet keine.

- `upgrade.sh` im Repo-Root (`100755`): Sicherung, Prüfung, Laden der Zielversion, `.env`, abgesicherter Start, Bereitschaft
- Smoke-Abschnitte „UPDATE OK“ und „UPDATE-ABBRUCH OK“ mit Pull-Spy und dem Weg zurück über `restore.sh`
- Abschnitt „Update“ auf der Installationsseite; README ohne eigene Update-Anleitung und ohne Demo-Anleitung für ältere Installationen; Konzept §14 auf dem umgesetzten Stand

## Flagged Assumptions

- **Demo-Elternkonto aus einer Installation von vor Phase 1 (03-RESEARCH L2): weggelassen, auch im README.** Veröffentlicht war nur `origin/master` (`6a918e8`, App-Code wie `4ce32da`). Dort legte `setup.sh` die Secrets mit `chmod 600` an (`git show 4ce32da:setup.sh` Z. 36), die API lief als `USER wordquest` (`4ce32da:backend/Dockerfile` Z. 39) und las den JWT-Schlüssel vor Migration und Seed (`4ce32da:backend/src/WordQuest.Api/Program.cs` Z. 18, 158-163); der rote Lauf steht in `.planning/quick/261006-r7l-installer-rechte-lesbare-docker-secrets-/261006-r7l-VERIFICATION.md` Z. 14. Eine solche Installation startete die API nie, ein Demo-Konto entstand nicht. Seit Phase 1 hat `.env.example` `WQ_SEED_DEMO_DATA=false`, und `setup.sh:77-80` bricht bei `true` ab. Sicherheitsnetz ohne neuen Code: `DemoAccountCheck` bricht den Start ab und nennt den Befehl; `upgrade.sh` verweist bei fehlender Bereitschaft auf `docker compose logs api`. Dieselbe Begründung trägt die Bereinigung des README-Abschnitts „Demo-Daten“ (Plan-Checker BLOCKER, D-10).
- **Update-Weg (D-05):** `git pull` und danach `./upgrade.sh`. Kein `git`-Aufruf im Skript (Bash liest das laufende Skript nach, 03-RESEARCH A6; der Smoke läuft in einer Arbeitskopie ohne `.git`).
- **Reihenfolge innerhalb von D-05:** Laden mit der Zielversion als Shell-Variable vor dem Schreiben der `.env` (03-RESEARCH Befund 5), damit ein fehlendes Image keinen halben Zustand hinterlässt.
- **Ältere Version und Pull im Smoke (Review 03-03 MEDIUM, L17@892d3de):** Es gibt keine veröffentlichten Images. Der Smoke benennt die gebauten Images zusätzlich als `0.0.0-smoke` (alt), die Zielversion `1.0.0` stammt aus dem Build in 03-01. Ab dem Update-Abschnitt gilt `COMPOSE_FILE=docker-compose.quick.yml` ohne Build-Overlay, damit Compose api und web als zu ladende Images behandelt. Ein kleiner Pull-Spy (Wrapper `docker` vorn im `PATH`, nur für den `upgrade.sh`-Aufruf) protokolliert bei `docker compose pull` die übergebene Zielversion und den Stand der `.env` und meldet Erfolg; alle anderen Docker-Befehle gehen an das echte `docker`. Belegt sind damit Zielversion, Reihenfolge und Start der Zielversion; der echte Pull aus GHCR ist Nach-Release-Abnahme (03-VALIDATION). Keine lokale Registry: Das wäre ein neues Image (T-03-SC).
- **Startfehler (Review 03-03 HIGH, L16@892d3de):** Health-Fehler über `WQ_SEED_DEMO_DATA=true` in `.env` (die API bricht in Production ab, `Program.cs:34-41`, Vorschlag aus 03-REVIEWS L84@892d3de). Direkter Fehler von `up -d` über eine Zielversion ohne Image, während der Spy Erfolg meldet: Compose will das Image beim Start laden und scheitert. Kein automatisches Zurückrollen; die Meldung nennt den Weg, und der Smoke geht ihn mit `restore.sh`.
- **Rechte von backups/:** `upgrade.sh` ändert keine Rechte, prüft nur den Besitz wie `setup.sh:56` (Pitfall 8).
- **Anmelde-Limit:** Der Abschnitt meldet sich nur nach API-Neustarts an (je eine Anmeldung); `auth_budget` aus 03-01 prüft das.
