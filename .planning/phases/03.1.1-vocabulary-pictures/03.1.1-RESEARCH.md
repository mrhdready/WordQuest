## Summary

Die Phase braucht **kein neues Paket** und **keine Änderung an nginx, Traefik, CSP oder Service Worker**. Alles Nötige ist im Bestand: `byte[]` ↔ `bytea` in Npgsql, `HttpRequest.Body` in Minimal APIs, `createImageBitmap` + Canvas + `toBlob` im Browser, `FileReader.readAsDataURL` für die Anzeige, `img-src 'self' data: blob:` in der CSP. In dieser Session gemessen: Chromium 156 dreht ein JPEG mit EXIF-Orientierung 6 korrekt (40×20 → 20×40), die WebP-Ausgabe enthält kein `Exif` mehr und beginnt mit `RIFF…WEBPVP`; dasselbe läuft ohne Secure Context (`isSecureContext: false`, kein `caches`, kein Service Worker). 500 Bilder à 50 KB ergeben eine `pg_dump | gzip`-Sicherung von 28,5 MB in 2,8 s, die Wiederherstellung in eine neue Datenbank dauert 1,8 s und liefert dieselben Bytes; die Vollständigkeitsprüfungen aus `restore.sh`/`upgrade.sh` greifen unverändert.

Die drei Leitentscheidungen dieser Recherche: (1) **Anzeige** über `api()` als Blob, im `queryFn` per `FileReader` in eine data-URL gewandelt und in TanStack Query unter `['picture', version]` gehalten. Das braucht kein `createObjectURL`/`revokeObjectURL`, also kein Speicherleck und keinen `setState` im Effekt. Den würde `react-hooks/set-state-in-effect="error"` im Lint ablehnen. Refresh und 401 laufen über die vorhandene Logik in `api()`. (2) **Upload** als roher Body (`PUT …/picture`, `Content-Type: image/webp|jpeg`), nicht `multipart/form-data`. Damit entfällt die Antiforgery-Frage von `IFormFile` ganz, und die Grenze von 300 KB setzt ein begrenztes Lesen im Endpoint. Das wirkt auch unter `WebApplicationFactory`, deren TestServer keine `IHttpMaxRequestBodySizeFeature` setzt; `[RequestSizeLimit]` wäre dort wirkungslos. (3) **Versionierung** über eine `Version`-Guid in der Bildzeile. Sie wird bei jedem Ersetzen neu vergeben, steht als `pictureVersion` in den DTOs und ist Teil der URL `GET /api/v1/pictures/{version}`. Ein ersetztes Bild hat damit eine neue URL und einen neuen Query-Key.

**Primary recommendation:** Tabelle `vocabulary_picture` (PK = `entry_id` wie `gamification_profile`, Spalten `version`, `data bytea`, Mandantenfilter). Dazu drei Endpoints in `PictureEndpoints.cs`, Logik in `PictureService` und `PictureRules`. Im Frontend `lib/picture.ts` mit `shrinkPicture()` und `usePicture()`; `api()` lernt Blob-Body und Blob-Antwort.

### Muster 1 (Frage 1, D-12/D-13): Anzeige über `api()` als Blob → data-URL

**Bewertung der drei Wege:**

| Kriterium | Blob + objectURL | signierte URL | data-URL im Runden-JSON | **Blob → data-URL im `queryFn` (Empfehlung)** |
|---|---|---|---|---|
| Neuer Server-Code | GET-Endpoint | GET ohne Auth + HMAC + Ablauf | keiner, aber Session-Builder lädt Bytes | GET-Endpoint |
| Ohne Anmeldung abrufbar? | nein | ja, im Gültigkeitsfenster | nein | nein |
| 401/Refresh | über `api()` | eigene Ablauflogik | über `api()` | über `api()` (`api.ts:234-236`) |
| Speicherleck | ja, ohne `revokeObjectURL` | nein | nein | nein (String im Query-Cache, GC nach `gcTime`) |
| Lint | `set-state-in-effect` = error | — | — | unkritisch |
| Eltern-Liste | ja | ja | nein (zweiter Weg nötig) | ja |
| Ohne HTTPS/SW | ja | ja | ja | ja (gemessen) |

Belege:
- `api()` setzt den Bearer-Header und wiederholt nach 401 einmal: `if (access) headers.Authorization = \`Bearer ${access}\`` und `if (response.status === 401 && retryOn401 && (await mayRetry(access, session))) {` `[VERIFIED: frontend/src/lib/api.ts:220, 234]`. Scheitert der Refresh mit 400/401, leert `tokenStore.clear()` die Anmeldung (`api.ts:149-151`), die Oberfläche folgt dem Speicher. Das Bild-Query endet dann mit `ApiError` und die Seite zeigt das Emoji (Fallback, Muster 7).
- Lint: `eslint-plugin-react-hooks` 7.1.1, `react-hooks/set-state-in-effect="error"`, `react-hooks/purity="error"` `[VERIFIED: node -e … configs.recommended in frontend/, diese Session]`.
- CSP erlaubt data-URLs: `img-src 'self' data: blob:` `[VERIFIED: frontend/nginx-security-headers.conf:11]`.
- Ohne Secure Context in Chromium gemessen: `{"secure":false,"bmp":[64,32],"webpType":"image/webp","dataUrlPrefix":"data:image/webp;base64,","hasCaches":false,"hasSW":false}` `[VERIFIED: Playwright Chromium 156, Host insecure.test, diese Session]`.
- D-13: Workbox cached jedes `GET /api/` als `NetworkFirst` in `cacheName: 'wq-api'` `[VERIFIED: frontend/vite.config.ts:37-44]`; `tokenStore.clear()` und `saveLogin()` rufen `dropApiCache()` → `caches.delete(API_CACHE)` mit `const API_CACHE = 'wq-api'` `[VERIFIED: frontend/src/lib/api.ts:10, 65-67, 80, 95-98]`. Bilder landen damit nur in `wq-api` (nur im HTTPS-Betrieb), **keine Änderung an `vite.config.ts` nötig**. Rest-Hinweis: `expiration: { maxEntries: 200, … }` (`vite.config.ts:43`) teilen sich Bilder und JSON; Offline-Lernen ist v2 (Konzept §2 Punkt 4), also ohne Folgen in 1.0.0.
- Antwort-Header `Cache-Control: no-store` am Bild-GET: hält Bilder aus dem HTTP-Plattencache gemeinsam genutzter Geräte. Wiederverwendung leistet TanStack Query im Speicher (`staleTime: Infinity`, weil eine `version` nie anderen Inhalt bekommt).

**Empfehlung:** `usePicture(version)` in `frontend/src/lib/picture.ts` (Code Examples). Kein `blob:`, kein `revokeObjectURL`, kein eigener Effekt.

|---|---|---|
| `image/png` | `89 50 4E 47 0D 0A 1A 0A` | `FF FF FF FF FF FF FF FF` |

### Muster 9 (Frage 4): nginx und Traefik

- nginx: „Default: client_max_body_size 1m;“ … „If the size in a request exceeds the configured value, the 413 (Request Entity Too Large) error is returned“ `[CITED: https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size]`. `frontend/nginx.conf` setzt den Wert nicht `[VERIFIED: grep client_ in frontend/*.conf leer]`. 300 KB < 1 MB → **keine Änderung**. Oberhalb von 1 MB antwortet nginx mit eigener HTML-413. Das trifft nur direkte API-Aufrufe (die App schickt ≤ 300 KB), `readError` zeigt dann den generischen deutschen Text `GENERIC` (`api.ts:263-265`).
- Traefik: Die Buffering-Middleware „limits the size of requests“, `maxRequestBodyBytes` Standard `0` = „unlimited“ `[CITED: doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/buffering/]`. `docker-compose.yml` konfiguriert keine Middleware `[VERIFIED: grep middleware/buffering leer]`. nginx hinter Traefik bleibt die Grenze → **keine Änderung**.
- Bodies > 8/16 KB puffert nginx in eine Temp-Datei (Warnung im Log) `[ASSUMED]`. Das Image `nginxinc/nginx-unprivileged:alpine` (`frontend/Dockerfile`) ist nicht read-only. Harmlos, nicht anfassen.

### Anti-Patterns to Avoid
- **`Include(e => e.Picture)` / `ThenInclude` in Listen oder Runde:** lädt `data` (bis 300 KB je Zeile). Immer projizieren.
- **`ToDictionaryAsync(p => p.Id, p => p.Version)` direkt auf `VocabularyPictures`:** materialisiert ganze Entitäten samt Bytes, weil der Element-Selector clientseitig läuft. Erst `.Select(p => new { p.Id, p.Version })` `[ASSUMED: EF-Verhalten; Messung über SQL-Log möglich]`.
- **Content-Type des Requests vertrauen:** nur Magic Bytes entscheiden.
- **`[RequestSizeLimit]` als einzige Grenze:** im TestServer wirkungslos, in Kestrel englischer 413-Text.
- **Hochladen vor dem Verkleinern prüfen statt danach:** maßgeblich ist die Blob-Größe nach `toBlob`.
- **Logik in `SetEndpoints.cs` dazuschreiben:** die Datei hat schon 381 Zeilen, und D-10 verlangt einen Service.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| EXIF-Drehung lesen | eigener EXIF-Parser | `createImageBitmap(…, { imageOrientation: 'from-image' })` | Browser kennt alle 8 Orientierungen, gemessen |
| Metadaten entfernen | APP1-Segmente ausschneiden | Neu-Kodierung über Canvas | Ausgabe enthält nachweislich kein `Exif` |
| Bildformat erkennen | Endungen, `Content-Type`, Bild-Bibliothek | WHATWG-Byte-Muster (3 Vergleiche) | Spezifiziert, kein Paket |
| Token-Refresh beim Bildabruf | eigener `fetch` mit Header | `api()` mit Blob-Option | Refresh-Rotation, 409-Fenster, Abmelden sind dort gelöst (`api.ts:116-204`) |
| Signierte URLs | HMAC + Ablauf | Bearer über `api()` | Kein Zeitfenster ohne Anmeldung |
| Bilddateien auf Platte | Volume + Pfade | `bytea` (D-06) | Sicherung/Restore/Update unverändert, gemessen |
| ObjectURL-Lebenszyklus | Effekt + revoke | data-URL im `queryFn` | Kein Leck, lint-konform |

**Key insight:** Jede Bild-Bibliothek (Server oder Client) wäre eine neue Dependency und größere Angriffsfläche. Browser-Kodierung plus Byte-Muster am Server deckt D-04/D-08 vollständig ab.

## Common Pitfalls

### Pitfall 1: Safari kodiert kein WebP und liefert still PNG
**What goes wrong:** `toBlob(cb, 'image/webp')` liefert in Safari `image/png`; ein 512-px-Foto als PNG kann 300 KB überschreiten (gemessen bis 902 KB) → 413.
**How to avoid:** `blob.type` prüfen, sonst JPEG 0.85 nach weißem Hinterlegen.
**Warning signs:** 413 nur bei Safari-Nutzern. Vitest-Fall „toBlob liefert image/png“ muss JPEG erzwingen.

### Pitfall 2: Grenze greift im Integrationstest nicht
**What goes wrong:** `[RequestSizeLimit]`/`IRequestSizeLimitMetadata` hängt an `IHttpMaxRequestBodySizeFeature`, das der TestServer nicht setzt.
**How to avoid:** begrenztes Lesen im Endpoint (Code Examples).
**Warning signs:** 413-Test grün ohne Grenze oder 200 auf 400-KB-Body.

### Pitfall 3: DTO meldet „kein Bild“, obwohl eines da ist
**What goes wrong:** `ToDto(entry)` in `UpdateEntryAsync`/`AddEntryAsync` sieht die nicht geladene Navigation `Picture` als `null`.
**How to avoid:** Version per Projektion nachladen; Test „Wörter ändern lässt `pictureVersion` stehen“.

### Pitfall 4: Bytes in Listen und Runden geladen
**What goes wrong:** `Include`/`ThenInclude` oder clientseitige Selektoren holen `data` mit, und die Liste mit 100 Vokabeln lädt 5–30 MB.
**How to avoid:** nur `Select(… Version …)`. Prüfbar im Integrationstest über die Antwortgröße oder per SQL-Log.

### Pitfall 5: Zwei Datei-Felder auf der Seite
**What goes wrong:** `page.locator('input[type="file"]')` (Muster aus `manage.spec.ts:227`) trifft bei offenem CSV-Import zwei Elemente.
**How to avoid:** im Dialog suchen (`page.getByRole('dialog').locator('input[type="file"]')`).

### Pitfall 6: Layoutsprung und Fokus beim Nachladen
**What goes wrong:** Das Bild erscheint erst nach dem Abruf und verschiebt Prompt und Eingabefeld (`autoFocus` am Input, `SessionPage.tsx:248`).
**How to avoid:** Rahmen fester Größe, sobald `pictureVersion` gesetzt ist; Bild darin `object-contain`.

### Pitfall 7: Transparente PNGs werden im JPEG-Fallback schwarz
**How to avoid:** `destination-over` + `fillStyle = 'white'` vor `toBlob('image/jpeg')`.

### Pitfall 8: Doppelklick legt zwei Zeilen an
**What goes wrong:** Zwei parallele PUTs auf eine Vokabel ohne Bild → PK-Konflikt → 500.
**How to avoid:** im UI wie überall `busyRef` (`SetDetailPage.tsx:428` in `EditEntry`). Server-Rest als akzeptierte Grenze notieren; der Fall braucht einen einzelnen Elternteil mit Doppel-Tab.

### Pitfall 9: Kein `URL.createObjectURL` in jsdom
**What goes wrong:** jsdom implementiert weder Canvas-Kontext noch `createImageBitmap` `[ASSUMED: jsdom-Grenze, vite.config.ts:56 environment 'jsdom']`.
**How to avoid:** In Vitest `createImageBitmap` per `vi.stubGlobal` und `HTMLCanvasElement.prototype.getContext`/`toBlob` per `vi.spyOn` ersetzen; Seiten-Tests mocken `@/lib/picture`. Die data-URL-Variante braucht nur `FileReader`, und der ist in jsdom vorhanden `[ASSUMED]`.

### Pitfall 10: Gesperrter Button verliert den Fokus
**What goes wrong:** Wird „Bild wählen“ während Verkleinern/Upload `disabled`, wandert der Fokus auf `body`. Der Quick-Task 261022-cb3 hat genau das korrigiert: `{/* Waehrend des Lesens nicht gesperrt: der fokussierte Button gaebe den Fokus sonst an body ab. */}` `[VERIFIED: SetDetailPage.tsx:756; Commit 99b99b6]`. `EditEntry` fängt verlorenen Fokus nach Fehlern auf „Abbrechen“ ab (`if (error && document.activeElement === document.body) cancelRef.current?.focus()`, `SetDetailPage.tsx:433-435`).
**How to avoid:** Doppelte Auslösung über `busyRef` verhindern, nicht über `disabled` am fokussierten Button; oder den Fokus nach Abschluss gezielt zurücksetzen. Test: Fokus liegt nach Upload und nach Fehler auf einem Element im Dialog.

### `PictureRules` (Modules.Content, rein, ohne EF/HTTP)
```csharp
namespace WordQuest.Modules.Content.Services;

/// <summary>Grenze und Formate fuer Vokabelbilder (D-08); Muster nach WHATWG MIME Sniffing.</summary>
public static class PictureRules
{
    /// <summary>300 KB: ungünstigster Fall 512 px als WebP/JPEG liegt bei rund 180 KB.</summary>
    public const int MaxBytes = 300 * 1024;

    private static ReadOnlySpan<byte> Png => [0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A];
    private static ReadOnlySpan<byte> Jpeg => [0xFF, 0xD8, 0xFF];

    /// <summary>Erkannter Typ oder null, wenn es kein WebP, JPEG oder PNG ist.</summary>
    public static string? DetectContentType(ReadOnlySpan<byte> data)
    {
        if (data.StartsWith(Png)) return "image/png";
        if (data.StartsWith(Jpeg)) return "image/jpeg";
        if (data.Length >= 14 && data[..4].SequenceEqual("RIFF"u8) && data[8..14].SequenceEqual("WEBPVP"u8))
        {
            return "image/webp";
        }
        return null;
    }
}
```
(Stil des Bestands: geschweifte Klammern auch bei Einzeilern, siehe `ContentRules.cs:33-38`.)

### Endpoint: begrenzt lesen, dann Service

```csharp
    Guid setId, Guid entryId, HttpRequest request, PictureService pictures, CancellationToken ct)
{

    int total = 0;
    int read;
    while (total < buffer.Length && (read = await request.Body.ReadAsync(buffer.AsMemory(total), ct)) > 0)
    {
        total += read;
    }

    if (total > PictureRules.MaxBytes)
    {
        return TooLarge();
    }

    // Service prueft Vokabel (404), leeren Inhalt und Magic Bytes (400) und speichert.
    return await pictures.SaveAsync(setId, entryId, buffer.AsMemory(0, total), ct);
}

private static IResult TooLarge() =>
    Results.Problem(
        title: "Zu groß",
        detail: "Das Bild ist zu groß. Erlaubt sind höchstens 300 KB.",
        statusCode: StatusCodes.Status413PayloadTooLarge);
```
Hinweis: Wenn `SaveAsync` ein `IResult` zurückgibt, steckt HTTP im Service. Sauberer ist ein kleines Ergebnis-Enum (Muster `ContentTextProblem`, `ContentRules.cs:30`), das der Endpoint auf `IResult` abbildet. Der Planner wählt.

```ts
import { useQuery } from '@tanstack/react-query'
import { api } from '@/lib/api'

const MAX_EDGE = 512

function encode(canvas: HTMLCanvasElement, type: string, quality: number) {
  return new Promise<Blob | null>((resolve) => canvas.toBlob(resolve, type, quality))
}

// Verkleinert, dreht nach EXIF und kodiert neu: dabei fallen EXIF/GPS weg (D-04).
export async function shrinkPicture(file: Blob): Promise<Blob> {
  const bitmap = await createImageBitmap(file, { imageOrientation: 'from-image' })
  const scale = Math.min(1, MAX_EDGE / Math.max(bitmap.width, bitmap.height))
  const canvas = document.createElement('canvas')
  canvas.width = Math.round(bitmap.width * scale)
  canvas.height = Math.round(bitmap.height * scale)
  const context = canvas.getContext('2d')
  if (!context) throw new Error('canvas')
  context.imageSmoothingQuality = 'high'
  context.drawImage(bitmap, 0, 0, canvas.width, canvas.height)
  bitmap.close()

  const webp = await encode(canvas, 'image/webp', 0.8)
  if (webp?.type === 'image/webp') return webp
  // Safari kodiert kein WebP und liefert dann PNG; JPEG kennt keine Transparenz.
  context.globalCompositeOperation = 'destination-over'
  context.fillStyle = 'white'
  context.fillRect(0, 0, canvas.width, canvas.height)
  const jpeg = await encode(canvas, 'image/jpeg', 0.85)
  if (!jpeg) throw new Error('encode')
  return jpeg
}

function toDataUrl(blob: Blob) {
  return new Promise<string>((resolve, reject) => {
    const reader = new FileReader()
    reader.onload = () => resolve(String(reader.result))
    reader.onerror = () => reject(reader.error)
    reader.readAsDataURL(blob)
  })
}

// Bild mit Anmeldung laden; eine Fassung aendert sich nie, deshalb staleTime Infinity.
export function usePicture(version: string | null) {
  return useQuery({
    queryKey: ['picture', version],
    queryFn: async () => toDataUrl(await api<Blob>(`/pictures/${version}`, { blob: true })),
    enabled: version !== null,
    staleTime: Infinity,
  })
}
```
